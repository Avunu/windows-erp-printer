# Development

The product is a .NET 10 solution. [architecture.md](architecture.md) covers the structure and the conventions every change must follow; this page covers building, testing, packaging, CI and releases.

## Layout

```
ErpPrinter.slnx                 the solution
Directory.Build.props           shared settings and THE VERSION (marked for release-please)
Publish.props                   publish settings of the three executables
nuget.config                    pins nuget.org
src/ErpPrinter.Core             portable logic (no Windows APIs): settings, secrets, outbox, backends, diagnostics decisions
src/ErpPrinter.Windows          registry, DPAPI, winspool, pipes, event log, service control, diagnostics checks, updater
src/ErpPrinter.Service          ErpPrinterService.exe  - the "ErpPrinter" Windows service
src/ErpPrinter.Cli              erpprinter.exe         - command line
src/ErpPrinter.Config           ErpPrinterConfig.exe   - configuration window (requires administrator)
tests/                          xUnit: Core.Tests (any OS), Windows.Tests, Config.Tests (Windows); E2E (disposable Windows machine)
installer/ErpPrinter.wxs        WiX v5 package
policies/                       ADMX/ADML, generated from the schema
assets/erp-printer.ico          generated by build/make-icon.py
build/                          build.ps1, Publish.ps1, Test-CommitMessage.ps1
.config/dotnet-tools.json       repo-local tools: WiX 5.0.2
```

The settings schema (`src/ErpPrinter.Core/Settings/Schema.cs`) drives the registry layer, validation, the configuration window, the ADMX templates and [settings.md](settings.md). After adding or changing a setting, run `./build/build.ps1 -Task Generate` and commit the regenerated files. A unit test fails if you forget.

## Build, test, publish, package

Prerequisites: the .NET 10 SDK, and Windows for the Windows projects, the publish and the MSI. WiX comes from the repo-local tool manifest, so nothing is installed globally; a different WiX on `PATH` (say a global 7.x) is never used.

```powershell
./build/build.ps1 -Task Build,Test                  # off Windows: only Core and its tests
./build/build.ps1 -Task Generate                    # after schema changes
./build/build.ps1 -Task Publish,Msi,Manifest `
  -Version 1.2.3 -UpdateManifestUrl https://github.com/<owner>/<repo>/releases/latest/download/latest.json
```

| Task | Result |
| --- | --- |
| `Build` | `dotnet build ErpPrinter.slnx -c Release` |
| `Test` | xUnit, TRX files in `out/test-results`. `-TestScope Core\|Windows\|All` |
| `Generate` | `policies/` and `docs/settings.md` from the schema, with `erpprinter schema` |
| `Publish` | `build/Publish.ps1`: the three executables, self-contained for `win-x64`, into **one** folder `out/payload`, plus `Policies\`, `README.md`, `LICENSE` |
| `Sign` | Authenticode-signs the product's own `erpprinter.exe`, `ErpPrinter*.exe` and `ErpPrinter*.dll` (`-CertificatePath`); runtime files are already signed |
| `Msi` | `out/ErpPrinter-<version>-x64.msi` (signed too if a certificate is given) |
| `Manifest` | `latest.json`, the `.sha256` file and the ADMX zip next to the MSI |

The version comes from `Directory.Build.props` (release-please bumps it) unless `-Version` is given. `-UpdateManifestUrl` and `-Commit` are stamped into `ErpPrinter.Core` as assembly metadata (`BuildInfo`). The solution has warnings as errors.

Design choices: **ReadyToRun** (faster service start), **self-contained** (no .NET prerequisite on customer machines), **no trimming or Native AOT** (the code uses reflection-heavy APIs), **no single-file** (three executables share one copy of the runtime, 110 MB uncompressed, about 40 MB in the MSI, and an upgrade just swaps plain files). Debug symbols are embedded in Release builds, so stack traces in logs carry line numbers.

The published layout the code may rely on:

```
C:\Program Files\ERP Printer\
  ErpPrinterService.exe        service host (also <name>.dll, .deps.json, .runtimeconfig.json, appsettings.json)
  erpprinter.exe               CLI
  ErpPrinterConfig.exe         configuration window, manifest requires administrator
  *.dll, hostfxr/hostpolicy…   the shared self-contained runtime and the app assemblies
  Policies\ErpPrinter.admx, Policies\en-US\ErpPrinter.adml
  README.md, LICENSE
```

## Tests

-   **Core.Tests** run anywhere and cover everything portable, with a fake registry, fake spooler, fake clock and a loopback HTTP server. **Windows.Tests** run real named pipes, DPAPI, an HKCU-rooted registry and read-only spooler calls, plus an end-to-end test (named pipe to listener to outbox to uploader to webhook) in which only the spooler is faked. Tests never write to HKLM, the real Application event log or the user's printers; anything that needs administrator rights or changes the real spooler is skipped unless `ERP_PRINTER_ADMIN_TESTS=1` is set in an elevated shell.
-   **Config.Tests** drive the real form on an STA thread against fake actions and save screenshots of each tab to `tests/ErpPrinter.Config.Tests/bin/.../screenshots`.
-   **`tests/E2E/Invoke-E2ETest.ps1`** installs the MSI with a webhook profile, prints through the real spooler, checks delivery, the retry path, `testprint` and `diagnose`, then uninstalls. **Run it only on a disposable machine.**

## The MSI

`installer/ErpPrinter.wxs`, WiX v5 (`WixToolset.Util.wixext` for the quiet-exec/shell-exec custom actions and service recovery).

**Service.** `ServiceInstall`: name `ErpPrinter`, display name "ERP Printer", `LocalSystem`, own process, automatic start. Recovery: restart after 60 s on every failure, counter reset after 1 day. `ServiceControl` stops the service on install/upgrade/uninstall (waiting for it), deletes it on uninstall, and starts it after install (without waiting). There is deliberately **no dependency on the Print Spooler**: stopping the spooler is a routine troubleshooting step and would stop a dependent service permanently, because recovery actions only fire on crashes. The service waits for the spooler itself.

**Custom actions** (both deferred, SYSTEM): `CA_Provision` runs `erpprinter.exe install "ProfileName=..." "Backend=..." ...` on install, upgrade and repair, after `InstallServices` and before `StartServices` (failure fails the installation); `CA_Deprovision` runs `erpprinter.exe uninstall "Purge=[PURGE]"` on a real uninstall only (skipped during an upgrade; result ignored). `install` is idempotent: it writes `InstallDir` and `InstalledVersion`, creates the data folder and secrets key, applies the `AutoUpdate`/`UpdateManifestUrl` globals, seeds the profile when `ServerUrl` is given, enables the PrintService operational log, ensures the Print to PDF driver, creates the printers and ports, registers the event source and removes the legacy scheduled tasks. It never starts or stops the service and never fails because a printer could not be provisioned (that is logged; `status` shows it). The install properties are listed in the [README](../README.md#install).

The upgrade from the PowerShell version and the reasoning behind keeping the UpgradeCode are in [upgrading.md](upgrading.md).

## CI

`.github/workflows/ci.yml` runs on pushes to `main` and on pull requests:

| Job | Runner | What it does |
| --- | --- | --- |
| Core tests | the self-hosted NixOS runner (`ubuntu-latest` for fork pull requests) | restore, build and test `ErpPrinter.Core.Tests` with the SDK from nixpkgs (`DOTNET_ROOT` is pointed at it because the runner exports its own) |
| Build, Windows tests and MSI | `windows-latest` | `Build,Test,Publish,Msi,Manifest`; uploads the MSI, the published payload and the test results. Versioned `0.0.<run number>` |
| End-to-end | `windows-latest` | installs the MSI, prints, verifies delivery to a local webhook, uninstalls. Marked `continue-on-error` until it has proven stable on the hosted image |

`.github/workflows/commits.yml` checks every commit in a pull request, and the pull request title, against the rules in [Commit messages](#commit-messages). Dependabot keeps the workflow actions and the NuGet packages current.

## Commit messages

Releases are driven by [Conventional Commits](https://www.conventionalcommits.org/), so commit messages decide the next version and the changelog:

| Commit | Release | Changelog section |
| --- | --- | --- |
| `fix(uploader): retry on HTTP 429` | patch | Bug Fixes |
| `feat(erpnext): attach to a document by template` | minor | Features |
| `feat!: ...` or a `BREAKING CHANGE:` footer | major (minor while below 1.0) | Breaking changes |
| `perf:`, `revert:` | patch | Performance Improvements, Reverts |
| `docs:`, `test:`, `ci:`, `build:`, `refactor:`, `style:`, `chore:` | none on their own | hidden |

Allowed types: `build`, `chore`, `ci`, `docs`, `feat`, `fix`, `perf`, `refactor`, `revert`, `style`, `test`. Useful scopes are the component names: `listener`, `uploader`, `config`, `installer`, `updater`, `diagnostics`, `odoo`, `erpnext`, `webhook`, `cli`.

Keep HTML-like tags out of the subject and any `BREAKING CHANGE:` note (write "the picture element", not the tag). release-please round-trips the release PR body through an HTML parser, and a raw tag there can silently drop the release. The checker rejects them.

`build/Test-CommitMessage.ps1` holds the rules. CI runs it on pull requests; to run it on every local commit:

```sh
git config core.hooksPath .githooks
```

If you squash-merge, the pull request title becomes the commit message, which is why CI checks the title too.

## Releases

Releases are automated with [release-please](https://github.com/googleapis/release-please) (`.github/workflows/release-please.yml`, configured by `release-please-config.json`):

1. Every push to `main` updates an open **release pull request** titled `chore(main): release X.Y.Z`. It bumps the version in `Directory.Build.props` (the line marked `x-release-please-version`) and adds the new commits to `CHANGELOG.md`.
2. Merging that pull request creates the `vX.Y.Z` tag and a GitHub release whose notes are the changelog entry.
3. The same workflow then calls `release-assets.yml`. That runs the tests on Windows, builds (and signs, if configured) the MSI, and attaches the MSI, `.sha256`, `latest.json` and the ADMX zip to the release.

Installed clients check `releases/latest/download/latest.json` daily and upgrade themselves, so **attaching the assets is what rolls a release out**. For the few minutes between the release appearing and its assets being attached, that URL returns 404; the updater logs this and tries again the next day. If an asset build fails, fix the problem and run **Release assets** manually (Actions tab) with the tag. Clients stay on the previous version until then.

Useful controls:

- **Force a version:** add a `Release-As: 1.0.0` footer to a commit on `main`.
- **Hold a release back:** do not merge the release pull request. Nothing is published, and clients stay where they are.

Repository settings this needs:

- **Settings > Actions > General > Workflow permissions:** allow GitHub Actions to create and approve pull requests, or release-please cannot open its pull request.
- Pull requests opened with the default `GITHUB_TOKEN` do not trigger other workflows, so CI does not run on the release pull request. If `main` requires status checks, either exempt that branch or give the action a GitHub App or fine-grained token via its `token` input.

### Code signing

Signing is optional; unsigned releases install and update normally. Unsigned MSIs trigger SmartScreen and *Unknown publisher* prompts on interactive installs (silent installs are unaffected), and application-control policies that require signed code will block unsigned executables.

The Microsoft Store is not needed for signing, and would not fit anyway: Store packages cannot create printers, ports or SYSTEM services. If you want signing later, any Authenticode code-signing certificate works. Low-cost options are Azure Trusted Signing (a monthly subscription, no hardware token) and SignPath's free plan for open-source projects. Both would replace the `.pfx` step below with their own signing action.

To sign with a `.pfx`, add two repository secrets:

- `SIGNING_CERT_BASE64`: the code-signing `.pfx`, base64-encoded (`[Convert]::ToBase64String([IO.File]::ReadAllBytes('cert.pfx'))`).
- `SIGNING_CERT_PASSWORD`: its password.

When they are present, the release workflow Authenticode-signs the product's executables and assemblies and the MSI, with an RFC 3161 timestamp. Clients can then require signed updates with `RequireSignedUpdates` or `UpdateSignerThumbprint`.

## Adding a backend

1. Implement `IBackend` in `src/ErpPrinter.Core/Backends/<Name>Backend.cs`: `SendAsync` uploads and returns the remote id; `TestConnectionAsync` returns a one-line success message or throws. Throw `ErpException(message, permanent: true)` for errors that retrying will not fix; anything else is retried with backoff. Use `ErpHttp` and `ErpHttp.AssertSuccess` for HTTP; they handle the proxy, timeouts and error classification.
2. Register it in `BackendRegistry` and add its name to `Schema.BackendNames`, plus any settings it needs with `Backends = ["<Name>"]`. The configuration window shows them automatically.
3. Add tests under `tests/ErpPrinter.Core.Tests/Backends`, run `-Task Generate`, and document it in [backends.md](backends.md).

## Architecture notes

- **Why a named pipe:** each spooler connection to the port is exactly one complete job. There are no partial files, overwrites or polling. If the listener is down, jobs wait in the queue. A fixed-name file port with a file watcher, by contrast, races on half-written files, overwrites and locked files.
- **Why a service:** it starts at boot, has unlimited run time, and Windows restarts it on failure. The listener, uploader and updater run in one process, each restarted on its own, so a bug in the updater cannot stop printing.
- **Listener:** one asynchronous pipe instance per enabled profile, each on its own task, so a slow job on one printer does not block another. It reloads profiles every 30 s and reconciles the Windows printers when they change. Before reading the pipe, it looks up the job that is in `Printing` state on that queue, to get the user and title.
- **Uploader:** single instance (global mutex). Woken by a named event when a job lands, otherwise polls. Writes are atomic (`.tmp` + rename). The sidecar is written after the PDF, so a sidecar means a complete PDF, and orphaned PDFs are adopted after five minutes.
- **MSI:** major upgrades, scheduled after `InstallInitialize`. The deprovision custom action is skipped during upgrades (`UPGRADINGPRODUCTCODE`), and the provision action is idempotent, so upgrades keep printers, configuration and the outbox.
