# Development

## Layout

```
src/
  ErpPrinter.ps1                 CLI entry point (scheduled tasks, MSI custom actions, admins)
  ErpPrinterConfig.ps1           Windows Forms configuration GUI
  erp-printer.ico                generated by build/make-icon.py
  Modules/ErpPrinter/
    ErpPrinter.psd1/.psm1        module manifest and loader
    BuildInfo.psd1               version, commit, default update URL (stamped by the build)
    Private/Schema.ps1           the settings schema, the single source of truth
    Private/Registry.ps1         registry wrappers (the only code that touches the registry)
    Private/Secrets.ps1          DPAPI helpers
    Private/Outbox.ps1           spool folder layout, sidecars, retry backoff
    Private/Http.ps1             HttpClient transport + error classification
    Private/Windows.ps1          pipe server, spooler job lookup, driver/port/printer plumbing
    Private/Tasks.ps1            scheduled task registration
    Backends/*.ps1               one file per ERP
    Public/*.ps1                 exported commands
installer/ErpPrinter.wxs         WiX v5 MSI
policies/                        ADMX/ADML generated from the schema
build/                           build.ps1, bootstrap.ps1, generators
tests/Unit                       Pester 5 tests (run anywhere)
tests/E2E                        end-to-end install/print/uninstall test (Windows, elevated)
```

The settings schema drives the registry layer, validation, the GUI form, the ADMX templates and [settings.md](settings.md). After adding or changing a setting, run `./build/build.ps1 -Task Generate` and commit the regenerated files. A unit test fails if you forget.

The product runs on **Windows PowerShell 5.1**, so:

- Keep the source ASCII-only (5.1 reads BOM-less files as ANSI; a test enforces this).
- Avoid PowerShell 7-only syntax and parameters. `PSUseCompatibleSyntax`/`PSUseCompatibleCommands` catch most of it, and CI runs the tests on both editions.
- Remember that PowerShell unrolls enumerable return values. `MultipartFormDataContent` is one, hence `Write-Output -NoEnumerate`.

## Build and test

```powershell
./build/bootstrap.ps1                    # pinned Pester and PSScriptAnalyzer for this edition
./build/build.ps1 -Task Lint, Test       # PowerShell 7 on Linux/macOS works too
./build/build.ps1 -Task Generate         # after schema changes
```

On Windows with WiX (`dotnet tool install --global wix --version 5.0.2`):

```powershell
./build/build.ps1 -Task Stage, Msi, Manifest -Version 1.2.3 `
  -UpdateManifestUrl https://github.com/<owner>/<repo>/releases/latest/download/latest.json
```

Output goes to `out/`: the MSI, `.sha256`, `latest.json` and the ADMX zip.

The unit tests replace the registry and DPAPI with in-memory fakes (`tests/Unit/TestHelpers.ps1`), and run a real loopback HTTP server to exercise the transport. The E2E test (`tests/E2E/Invoke-E2ETest.ps1`) installs the MSI with a webhook profile, prints through the real spooler, checks delivery and the retry path, then uninstalls. Run it only on a disposable machine.

## CI

`.github/workflows/ci.yml` runs on pushes to `main` and on pull requests:

| Job | What it does |
| --- | --- |
| Lint | PSScriptAnalyzer with the repo settings, including the Windows PowerShell 5.1 compatibility rules |
| Test | Pester on Windows PowerShell 5.1 and PowerShell 7; NUnit XML uploaded as an artifact |
| Build MSI | WiX v5 build, versioned `0.0.<run number>`; MSI, manifest and ADMX uploaded as an artifact |
| End-to-end | Installs the MSI on the runner, prints, verifies delivery to a local webhook, uninstalls. Marked `continue-on-error` until it has proven stable on the hosted image |

`.github/workflows/commits.yml` checks every commit in a pull request, and the pull request title, against the rules in [Commit messages](#commit-messages).

Dependabot keeps the workflow actions current.

## Commit messages

Releases are driven by [Conventional Commits](https://www.conventionalcommits.org/), so commit messages decide the next version and the changelog:

| Commit | Release | Changelog section |
| --- | --- | --- |
| `fix(uploader): retry on HTTP 429` | patch | Bug Fixes |
| `feat(erpnext): attach to a document by template` | minor | Features |
| `feat!: ...` or a `BREAKING CHANGE:` footer | major (minor while below 1.0) | Breaking changes |
| `perf:`, `revert:` | patch | Performance Improvements, Reverts |
| `docs:`, `test:`, `ci:`, `build:`, `refactor:`, `style:`, `chore:` | none on their own | hidden |

Allowed types: `build`, `chore`, `ci`, `docs`, `feat`, `fix`, `perf`, `refactor`, `revert`, `style`, `test`. Useful scopes are the component names: `listener`, `uploader`, `gui`, `installer`, `updater`, `odoo`, `erpnext`, `webhook`, `config`.

Keep HTML-like tags out of the subject and any `BREAKING CHANGE:` note (write "the picture element", not the tag). release-please round-trips the release PR body through an HTML parser, and a raw tag there can silently drop the release. The checker rejects them.

`build/Test-CommitMessage.ps1` holds the rules. CI runs it on pull requests; to run it on every local commit:

```sh
git config core.hooksPath .githooks
```

If you squash-merge, the pull request title becomes the commit message, which is why CI checks the title too.

## Releases

Releases are automated with [release-please](https://github.com/googleapis/release-please) (`.github/workflows/release-please.yml`, configured by `release-please-config.json`):

1. Every push to `main` updates an open **release pull request** titled `chore(main): release X.Y.Z`. It bumps the version in `ErpPrinter.psd1` and `BuildInfo.psd1` (the lines marked `x-release-please-version`) and adds the new commits to `CHANGELOG.md`.
2. Merging that pull request creates the `vX.Y.Z` tag and a GitHub release whose notes are the changelog entry.
3. The same workflow then calls `release-assets.yml`. That lints and tests on Windows PowerShell 5.1, builds (and signs, if configured) the MSI, and attaches the MSI, `.sha256`, `latest.json` and the ADMX zip to the release.

Installed clients check `releases/latest/download/latest.json` daily and upgrade themselves. For the few minutes between the release appearing and its assets being attached, that URL returns 404. The updater logs this and tries again the next day. If an asset build fails, fix the problem and run **Release assets** manually (Actions tab) with the tag. Clients stay on the previous version until then.

Useful controls:

- **Force a version:** add a `Release-As: 1.0.0` footer to a commit on `main`.
- **First release:** the config starts at `0.1.0`. release-please opens its first pull request once `main` has a `feat:` or `fix:` commit.

Repository settings this needs:

- **Settings > Actions > General > Workflow permissions:** allow GitHub Actions to create and approve pull requests, or release-please cannot open its pull request.
- Pull requests opened with the default `GITHUB_TOKEN` do not trigger other workflows, so CI does not run on the release pull request. If `main` requires status checks, either exempt that branch or give the action a GitHub App or fine-grained token via its `token` input.

### Code signing

Signing is optional; unsigned releases install and update normally. Unsigned MSIs trigger SmartScreen and *Unknown publisher* prompts on interactive installs (silent installs are unaffected). Unsigned scripts also cannot run where Group Policy enforces an `AllSigned` execution policy.

The Microsoft Store is not needed for signing, and would not fit anyway: Store packages cannot create printers, ports or SYSTEM scheduled tasks. If you want signing later, any Authenticode code-signing certificate works. Low-cost options are Azure Trusted Signing (a monthly subscription, no hardware token) and SignPath's free plan for open-source projects. Both would replace the `.pfx` step below with their own signing action.

To sign with a `.pfx`, add two repository secrets:

- `SIGNING_CERT_BASE64`: the code-signing `.pfx`, base64-encoded (`[Convert]::ToBase64String([IO.File]::ReadAllBytes('cert.pfx'))`).
- `SIGNING_CERT_PASSWORD`: its password.

When they are present, the release workflow Authenticode-signs every script in the payload (so the product also runs under an `AllSigned` execution policy) and the MSI, with an RFC 3161 timestamp. Clients can then require signed updates with `RequireSignedUpdates` or `UpdateSignerThumbprint`.

## Adding a backend

1. Create `src/Modules/ErpPrinter/Backends/<Name>.ps1` with:

   ```powershell
   function Send-Erp<Name>Document {
       param($PrinterProfile, $GlobalSettings, $Meta, [string] $PdfPath, [string] $FileName, [hashtable] $Secrets)
       # Upload and return the remote id. Throw New-ErpException '...' -Permanent for errors
       # that retrying will not fix; anything else is retried with backoff.
   }
   function Test-Erp<Name>Connection {
       param($PrinterProfile, $GlobalSettings, [hashtable] $Secrets)
       # Return a one-line success message or throw.
   }
   ```

   Use `Invoke-ErpHttp` + `Assert-ErpHttpSuccess` for HTTP; they handle the proxy, timeouts and error classification.
2. Add `<Name>` to `$script:ErpBackendNames` in `Private/Schema.ps1`, and add any settings it needs with `-Backends @('<Name>')`. The GUI shows them automatically.
3. Add tests to `tests/Unit/Backends.Tests.ps1`, run `-Task Generate`, and document it in [backends.md](backends.md).

## Architecture notes

- **Why a named pipe:** each spooler connection to the port is exactly one complete job. There are no partial files, overwrites or polling. If the listener is down, jobs wait in the queue. A fixed-name file port with a FileSystemWatcher, by contrast, races on half-written files, overwrites and locked files.
- **Why scheduled tasks and not a service:** Windows PowerShell cannot host a service without a wrapper. The tasks start at boot, have unlimited run time, and have a 5-minute watchdog trigger with `IgnoreNew`, so a crashed loop is restarted.
- **Listener:** one process, one asynchronous pipe instance per enabled profile. It reloads profiles every 30 s and reconciles the Windows printers when they change. Before reading the pipe, it looks up the job that is in `Printing` state on that queue, to get the user and title.
- **Uploader:** single instance (global mutex). Woken by a named event when a job lands, otherwise polls. Writes are atomic (`.tmp` + rename). The sidecar is written after the PDF, so a sidecar means a complete PDF, and orphaned PDFs are adopted after five minutes.
- **MSI:** major upgrades, scheduled after `InstallInitialize`. The deprovision custom action is skipped during upgrades (`UPGRADINGPRODUCTCODE`), and the provision action is idempotent, so upgrades keep printers, configuration and the outbox.
